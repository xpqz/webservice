Issues Service Design

A GitHub-Issues-shaped REST service: Postgres at the bottom, a pool of Dyalog workers on Stark in the middle, nginx in front, and a Vue console as one client among many. This is the map of how it fits together and why it is built the way it is.

4compose services, workers scaled to N
15routes, all copied from GitHub
~210lines of APL code in the service
150end-to-end checks in smoke.sh

1The whole system

Every request from a client goes to nginx on port 8080. nginx hands it to one of the identical workers. The worker validates the input, runs one or two SQL statements, and returns the JSON document Postgres built. The console is a fourth container that only serves static files; once the page is in the browser, the browser is the client.

Read top-down, the layers divide the work like this:

LayerOwnsDeliberately does not
nginxThe only public API port, load balancing, live discovery of workers, the X-Worker headerAny knowledge of the API

2Decisions that shaped it

Five decisions explain almost every detail further down. When something looks odd, it is usually one of these.

  1. A
    Copy GitHub, invent nothing. URLs, field names, status codes, error bodies (message, errors[{resource, field, code}]), pagination (per_page max 100, page) and sort=updated are GitHub's. Where GitHub has no simple equivalent, the skis feature was dropped: issue types, links, soft delete, full-text search.
    So the post never has to defend an API decision.
  2. B
    Standard tools do standard jobs. nginx balances, compose restarts, Postgres enforces rules, Jarvis speaks HTTP.
    The point of the post: APL is one component in an ordinary stack.
  3. C
    Postgres builds the JSON. The *_doc views and list functions return finished GitHub-shaped documents. A handler never assembles a response field by field.
    It removes most of the APL, and it makes null, timestamps and nested labels Postgres's problem.
  4. D
    Workers are stateless and identical. Each holds one database connection and nothing else, so any worker can answer any request and nginx can round-robin blindly.
    That is what makes --scale worker=N and "kill one, nothing breaks" true.
  5. E
    Failure is handled by restarting. A worker that loses its database connection exits; compose starts a fresh one.
    No reconnect logic in APL.

Start-up order

The worker image

Plain Debian plus four things, all fetched at build time: Dyalog 20.0's own .deb from dyalog.com (architecture picked by dpkg --print-architecture, so arm64 and x86-64 both build natively), unixodbc and odbc-postgresql from apt, and Stark v0.2.4 plus its bundled Jarvis as two raw files from GitHub. Tatin is not used: the "without Tatin" route Stark documents is two ADD lines and needs nothing interactive. App code is COPY'd in, not mounted, so after editing worker/ you rebuild with --build.

The repository never contains Dyalog. The README puts the licence notice before the first build command, and the licence ships in the image at /opt/mdyalog/20.0/64/unicode/LICENSE.

Two things in the return path are worth knowing. Jarvis re-encodes whatever the handler returns with ⎕JSON, so keys come out alphabetical and anything above ASCII is escaped (⍳ becomes ⍳); both are valid JSON. And because the handler only hands back what Postgres produced, a response's shape is defined in exactly one place: the view.

Every handler follows the same three steps. CreateComment is typical:

T and I are the bind-variable markers :<C100000(Q): (wide text) and :<I:. The values travel separately from the SQL text, so quotes and -- in user input are inert.

6Errors and exits


A request can leave a worker by five routes. Which one it takes is decided in three places: Stark (no route), the handler (input and existence), and Db.Check (SQL outcome).



Every 4xx body is GitHub's: {"message":"Not Found"} or {"message":"Validation Failed","errors":[{"resource":"Issue","field":"title","code":"missing_field"}]}. A 500 says only Server Error to the client and writes ERROR method path: EM SQLSTATE EN to docker compose logs worker.








7The database


Four tables adapted from skis, and a layer of SQL objects on top that does the work an application server would usually do.




The close/reopen rules


GitHub's state rules live in a BEFORE UPDATE trigger, issue_state_rules. APL only checks that state and state_reason are allowed words; it never sets closed_at.

8SQAPL in practice


SQAPL to psqlODBC is the least documented hop and where most of the build time went. The rules that came out of it, with the symptom each one prevents:



  
RuleOtherwise

  
    
Connect DSN-less: Driver={PostgreSQL Unicode};Server=… via DriverOptions, plus MaxRows 1An odbc.ini to manage; large output buffers reserved for many rows

    
Write CAST(x AS text), never x::textSQAPL reads : as a bind marker: syntax error at or near ":"

    
Never put data in SQL text; always bindNon-ASCII in statement text arrives as Latin-1 bytes or fails with 10081

    
Declare text wide: :<C100000(Q): in, :>C10000000(Q): outUTF-8 bytes come back as Latin-1 mojibake

    
Size every output declaration; treat rc ¯1 as an errorResults silently cut at 8190 chars, then ⎕JSON fails

    
Wrap writes that may match nothing: WITH d AS (DELETE … RETURNING id) SELECT id FROM dpsqlODBC reports HY010 Function sequence error for zero-row RETURNING

    
Pass arguments as (⊂sql),valuessql,values glues numbers onto the SQL string

  



Known gap: SQAPL passes wide text as UCS-2, so characters outside the Basic Multilingual Plane (emoji) are silently dropped in both directions. APL glyphs and accented letters are fine.

10The console


A separate client: four static files (index.html, style.css, api.js, app.js), Vue 3.5.13 imported from unpkg through an import map, no npm and no build step. The browser loads the files from :3000 and then calls :8080.



Behaviour worth knowing: on load it opens the newest open issue, or the most recently updated closed one (sort=updated). Clicking a label pill filters the list. Both dividers drag. Errors from the API (message and field errors) show inline. The API base is location.hostname:8080, so it also works from another machine on the network.








11Scaling and recovery


Scaling


nginx resolves worker through Docker's DNS (resolver 127.0.0.11 valid=5s, server worker:8080 resolve, which needs nginx 1.27.3 or later). docker compose up -d --scale worker=5 on a running stack is picked up within five seconds without touching nginx. The same five-second window explains the one flaky moment in testing: right after workers are replaced, nginx can still route to an old address and return 502.

12Tests


test/smoke.sh is bash, curl and jq against nginx, the way a client sees the service. It waits until /health answers through nginx, then runs every test_* function (or the ones named on the command line). Each run tags its data with a unique suffix, so tests never need an empty database. 150 checks currently pass.

13Limits and loose ends


Documented limitations


    
  
  • Emoji and other non-BMP characters are dropped (SQAPL, UCS-2).
    • 
  
  • A label whose name contains / can be created but not reached at /labels/{name}: Jarvis URL-decodes the whole path (Jarvis.aplc:1573) before Stark matches routes. An upstream issue for dyalog-labs/stark is drafted, not filed.
    • 
  
  • An empty string means "not sent", so a PATCH cannot clear an issue body or a label description.
    • 
  
  • JSON keys come back alphabetical, non-ASCII as \u escapes.
    • 
  
  • A few seconds of errors while Postgres restarts.
    • 
  
  • Stark is pre-release; pinned at v0.2.4.
    • 




  Minor issues found in review, deliberately left
  
    
    
  • DELETE /labels/{name} answers 204 with a 2-byte body ("").
    • 
    
  • Label create/rename maps every SQL error to 422 on name, which can hide other faults.
    • 
    
  • POST /issues/{n}/labels ignores GitHub's bare-array body form (["bug"]) and {}.
    • 
    
  • PATCH to a missing issue with unknown labels returns 422 before 404.
    • 
    
  • A non-JSON body gets Jarvis's empty 400, not GitHub's Problems parsing JSON; JSON5 syntax is accepted.
    • 
    
  • A NUL character truncates text.
    • 
    
  • A failure to connect at boot is logged as "Lost database connection".
    • 
    
  • Creating an issue and attaching its labels are separate statements, not one transaction.
    • 
  





  Calls made on your behalf that you may want to revisit
  
    
    
  • Business rules in Postgres (trigger, functions) rather than APL. It minimises APL, at the cost of the post having little APL "business logic" to point at; input validation is what remains.
    • 
    
  • Unknown label names on an issue → 422 rather than auto-creating labels.
    • 
    
  • X-Worker carries the worker's IP:port (nginx's $upstream_addr), not a hostname.
    • 
    
  • Wrong-typed fields are rejected by signalling EN 422 from a helper and shaping the error in Stark's error hook, guessing the resource name from the route.
    • 
    
  • The console loads Vue from unpkg, so it needs internet access in the browser.
    •
